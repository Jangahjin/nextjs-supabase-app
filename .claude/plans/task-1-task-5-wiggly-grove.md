# 정산·카풀 기능 수동 테스트 계획 (Task 1~5)

## Context

shrimp-task-manager Task 1~5(정산 기능 커밋, 카풀 테이블/RLS, 카풀 매칭 함수/알림, 카풀 UI, 문서 마감)를 모두 완료하고 6개 커밋으로 반영했다. 그동안의 검증은 대부분 `execute_sql`로 DB 함수를 직접 호출하거나(Task 3), 한 계정(owner)만으로 브라우저 골든 패스를 확인한 것(Task 4)이라 — 실제 두 사람이 서로 다른 역할(운전자/탑승자, 관리자/일반 멤버)로 상호작용할 때의 동작과, RLS가 비멤버를 실제로 차단하는지는 아직 검증되지 않았다. 사용자가 직접 두 개의 실제 Google 계정(`snita8379@gmail.com` = 그룹 owner, `t2684258@gmail.com` = 아직 비멤버)으로 브라우저에서 크로스 계정 시나리오를 검증하고 싶어해, 그 순서와 각 단계에서 무엇을 확인해야 하는지 정리한다.

새 이벤트로 처음부터 테스트하며(기존 `djhdjdjd` 이벤트는 건드리지 않음), 두 계정 모두 실제 로그인이 가능하다는 전제로 계획을 짠다.

## 사전 정보

- 그룹: "테스트 수영 모임ㄱ" (`b11404e7-4dcb-40f9-8957-742d6eb06d06`), owner = `snita8379@gmail.com`
- 두 번째 계정 `t2684258@gmail.com`은 `profiles`에는 있지만 `group_members`에는 아직 없음(비멤버) — 이 상태를 Phase 1의 RLS 차단 테스트에 그대로 활용한다

- 카풀 폼: `components/carpool/{carpool-offer-form,carpool-request-form,carpool-match-list}.tsx` / 매칭 실행: `app/groups/[groupId]/events/[eventId]/carpool/actions.ts` → `run_carpool_matching()` RPC
- 두 브라우저(또는 시크릿 창)를 열어 A = owner 계정, B = 두 번째 계정으로 동시에 로그인해두면 알림 실시간 반영을 바로 확인할 수 있다

## Phase 1 — 비멤버 RLS 차단 확인 (B 계정, 아직 그룹 가입 전)

B 계정으로 로그인한 상태에서 그룹/이벤트 URL에 직접 접근한다.

1. `http://localhost:3000/groups/b11404e7-4dcb-40f9-8957-742d6eb06d06` 접속 → **기대**: `groups_select_member` 정책상 pending 신청조차 없으므로 그룹 정보가 보이지 않거나(404/빈 화면) 홈으로 리다이렉트됨. 최소한 그룹 이름·멤버 목록·공지·일정이 노출되면 안 됨
2. 같은 그룹의 아무 이벤트/정산/카풀 URL에 직접 접근(예: `.../events/<id>` 형태로 추정 시도) → **기대**: `is_group_member` 기반 select 정책에 걸려 데이터가 비거나 접근이 막힘
3. 이 단계는 Task 2에서 검증한 RLS 정책이 실제 브라우저에서도 동일하게 동작하는지 확인하는 목적 — 여기서 뚫리면 마이그레이션의 select 정책을 재점검해야 함

## Phase 2 — 가입 승인 + 이벤트 RSVP 승인 (사전 준비, 기존 기능)

정산/카풀 테스트의 전제조건을 만드는 단계로, 이번에 새로 만든 기능은 아니다.

1. A: 이벤트 생성(`/groups/.../events/new`) — 제목 예: "정산·카풀 테스트 모임", 시작일시는 미래로
2. B: `/groups/join/<invite_code>`로 가입 신청(초대코드는 A가 그룹 홈 또는 설정에서 확인)
3. A: 멤버 관리 페이지에서 B의 가입 승인 → **확인**: B의 알림 벨에 "모임 가입이 승인되었습니다." 알림 도착
4. A, B 둘 다 새 이벤트에서 "참석 신청하기" 클릭
5. A: 참여자 관리 페이지에서 A·B 모두 승인 → **확인**: B의 알림 벨에 "참석 신청이 승인되었습니다: ..." 알림 도착

## Phase 3 — 정산 기능 (Task 1)

이벤트 상세 페이지 → "정산" 링크로 이동.

1. A(관리자)만 정산 생성 폼이 보이는지 확인 — B는 정산이 아직 없을 때 "아직 정산이 생성되지 않았습니다." 문구만 보이고 생성 폼은 없어야 함(`settlement/page.tsx`의 `!isAdmin` 분기)
2. A: 총액을 **2로 나누어 떨어지지 않는 금액**으로 입력(예: 10,001원) 후 생성 → **확인**: `floor(10001/2)=5000`을 기본으로, 나머지 1원이 **먼저 RSVP를 신청한 사람**(applied_at 오름차순)에게 추가되어 5001원/5000원으로 정확히 나뉘는지
3. B: 본인 항목의 체크박스만 활성화되어 있고 A의 항목 체크박스는 비활성화(disabled)인지 확인 → B가 본인 것 체크 → "입금완료"로 바뀌는지
4. A: 관리자이므로 A·B 항목 둘 다 체크/해제 가능한지 확인
5. 상단 요약 카드의 "N/M명 입금완료 · 미입금 합계 ..." 숫자가 체크 상태에 맞춰 정확히 갱신되는지 확인

## Phase 4 — 카풀 기능 (Task 2~4)

같은 이벤트 상세 페이지 → "카풀" 링크로 이동.

1. A: 운전자 offer 등록 — 출발 지역 "강남역", 좌석 수 2
2. B: 탑승 request 등록 — 출발 지역 "강남역 "(끝에 공백 포함, `departure_area_norm` 정규화 확인용)
3. A(관리자)만 "카풀 자동 매칭 실행" 버튼이 보이는지 확인(B 화면에는 없어야 함)
4. A: "카풀 자동 매칭 실행" 클릭 → 매칭 테이블에 "A (강남역) ↔ B (강남역 )" 행이 상태 "제안됨"으로 나타나는지 확인(공백 무시 매칭 확인)
5. A: "확정" 클릭 → 상태가 "확정"으로 바뀌는지 확인
6. **A, B 둘 다** 알림 벨에 "카풀 매칭이 확정되었습니다." 알림이 도착하는지 확인(Task 3에서 SQL로만 검증했던 2인 알림 팬아웃을 실제 두 계정으로 재확인하는 핵심 단계)
7. A: "카풀 자동 매칭 실행"을 한 번 더 클릭(재실행) → **확인**: 방금 confirmed로 바꾼 매칭이 사라지지 않고 그대로 "확정" 상태 유지(멱등성)
8. (선택, 폴백 배정 확인) 세 번째 지역 이름(예: "홍대")으로 B 계정이 아닌 또 다른 request를 추가할 계정이 없다면 이 단계는 SQL로 대체 가능 — Task 3에서 이미 검증했으므로 생략 가능

## Phase 5 — 문서 확인 (Task 5, 코드 리뷰성)

브라우저 테스트 대상이 아니라 육안 검토로 충분하다.

1. `CLAUDE.md`의 "데이터베이스" 절과 `docs/guides/project-structure.md`의 `app/`·`components/` 트리를 열어, 실제 폴더 구조(특히 방금 만든 `carpool/`)와 일치하는지 훑어본다

## 정리(선택)

테스트로 만든 이벤트·offer·request·match·notifications·settlement 데이터를 남겨둘지, 정리할지는 사용자가 결정한다. 정리하고 싶다면 이벤트를 삭제하면 `on delete cascade`로 참여자/정산/카풀/관련 알림까지 한 번에 정리된다(UI에 이벤트 삭제 기능이 없으므로 필요시 알려주면 SQL로 대신 정리해줄 수 있음).

## 검증 완료 기준

- Phase 1: 비멤버 B가 그룹/이벤트 데이터를 전혀 볼 수 없음
- Phase 3: 나머지 분배가 정확하고, 입금 체크 권한이 본인/관리자로만 제한됨
- Phase 4: 지역 정규화 매칭, 관리자 전용 매칭 버튼, confirmed 알림 2건(양쪽 계정), 재실행 멱등성이 모두 확인됨
- 위 세 항목이 모두 통과하면 Task 1~5가 실사용 시나리오에서도 설계대로 동작함이 최종 확인된 것
